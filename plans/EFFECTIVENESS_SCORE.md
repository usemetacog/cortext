# Design: Session Effectiveness Score — Correlating Prompt Quality to Output

Generated by /office-hours on 2026-05-18
Branch: main
Repo: cortext
Status: APPROVED
Mode: Builder

## Problem Statement

cortext currently measures prompt quality in isolation: vagueness score, correction
rate, category. It tells you *how* you prompted, not *whether it worked*. The gap is
that there's no signal connecting prompting behavior to session output — did this
session produce shipped code or just exploration?

The broader vision: eventually show team-level intelligence (who prompts effectively
under pressure, which patterns correlate with fewer bugs, who's improving fastest).
That requires a causal chain from prompt → session → outcome that doesn't exist yet.

## Constraints

- Must work entirely from existing ~/.claude/projects/ JSONL data (no new data sources)
- Zero onboarding friction — existing cortext users get the new metric on next run
- Weekend-scale build (S effort)
- Open source, no backend required

## Premises

1. Tool call ratio (Write/Edit calls / total tool calls per session) is a usable proxy
   for "this session produced real output" — imperfect but directionally correct.
2. Improving individual prompt quality will correlate with measurable team-level
   outcomes; the individual signal is the foundation.
3. The JSONL log is cortext's data moat — prompt-level interaction data that outcome
   tools don't have. Git/PR outcome data is commoditized but needed to close the loop
   eventually (Approach B).
4. Solo dev first, team second — the individual flywheel has to be compelling before
   mandated team rollout makes sense.

## Approaches Considered

### Approach A: Session Effectiveness Score (chosen)
Add `effectivenessScore` to SessionStats: `(writeEditCalls / totalToolCalls)` for
sessions with ≥ 5 tool calls. Overlay against specificity buckets in the dashboard.
- Effort: S (2-3 days, changes in analyzer.ts, types.ts, renderer.ts only)
- Risk: Low — purely local, no new infrastructure

### Approach B: Git-Correlated Outcome Pipeline
Connect session timestamps to git commits. Sessions ending within ~15 minutes of a
commit are tagged "shipped." Produces real ground truth, enables team features.
- Effort: M (1-2 weeks)
- Risk: Med — time-window correlation is fuzzy, breaks for infrequent committers
- *Natural next step if Approach A validates the hypothesis*

### Approach C: Self-Reported Outcome Tags + Community Benchmark
Post-session prompt: "Ship something? [y/n/partial]". Community anonymized aggregate
becomes a benchmark dataset.
- Effort: M — requires behavior change, self-report bias
- *Held for later if community features become relevant*

## Recommended Approach

**Approach A.** Validate the hypothesis with existing data before investing in git
integration. If "specific" sessions (median prompt vagueScore < 3) have a median
effectiveness score more than 0.10 higher than "vague" sessions, that's the empirical
foundation for Approach B.

### Implementation sketch

**Step 0: Verify tool names (required before Step 3)**

Run this against your own logs before defining `PRODUCTIVE_TOOLS`:

```bash
grep '"tool_use"' ~/.claude/projects/*/*.jsonl | \
  grep -o '"name":"[^"]*"' | sort | uniq -c | sort -rn | head -20
```

Wrong casing produces all-zero scores with no error. Use exact strings from your
output. Typical Claude Code names: `Write`, `Edit`, `Read`, `Bash`, `MultiEdit`,
`NotebookEdit`. Confirm before proceeding.

**Step 1: New fields on `SessionStats` in `types.ts`**

```typescript
// Add to SessionStats interface:
effectivenessScore: number | null; // write/edit ratio; null if < MIN_TOOL_CALLS
medianVagueScore: number | null;   // null when session has no user prompts
```

**Step 2: New aggregate on `AnalysisResult` in `types.ts`**

```typescript
// Add to AnalysisResult interface — two specificity buckets, not per-category:
effectivenessByBucket: {
  specific: number | null; // median effectivenessScore for sessions where
                           //   medianVagueScore < 3; null if N < 2
  vague: number | null;    // median effectivenessScore for sessions where
                           //   medianVagueScore >= 3; null if N < 2
};
medianEffectivenessScore: number | null; // overall median across all scored sessions
```

**Step 3: Per-session calculation in `analyzer.ts`**

Add two module-level constants (outside `analyze()`, alongside `MODEL_PRICING`):

```typescript
// Module-level — defined once, not per-session
const PRODUCTIVE_TOOLS = new Set(['Write', 'Edit', 'MultiEdit', 'NotebookEdit']);
const MIN_TOOL_CALLS = 5;
```

Inside `analyze()`, inside `for (const [sessionId, entries] of sessionEntries)`,
declare per-session accumulators alongside `sessionPromptVagueScores` after
`sessionStat` is initialized:

```typescript
let productiveToolCalls = 0;
let totalSessionToolCalls = 0;
const sessionPromptVagueScores: number[] = [];
```

Inside the `for (const entry of sorted)` loop, replace the existing assistant block
(lines ~147–153 in analyzer.ts) with the version below. The existing
`allToolCalls.push(block.name)` is preserved inside the same loop — do not add
a second push:

```typescript
if (entry.type === 'assistant' && entry.message?.usage) {
  // ... existing usage/cost/daily accounting unchanged ...

  if (Array.isArray(entry.message?.content)) {
    for (const block of entry.message.content as Array<{ type: string; name?: string }>) {
      if (block.type === 'tool_use' && block.name) {
        // existing aggregate push — keep exactly as-is:
        allToolCalls.push(block.name);
        // new per-session counters:

          totalSessionToolCalls++;
          if (PRODUCTIVE_TOOLS.has(block.name)) productiveToolCalls++;
        }
      }
    }
  }
  // ... rest of assistant branch unchanged ...
}
```

Inside the `entry.type === 'user'` branch, alongside the existing
`allPrompts.push(...)` call, add:

```typescript
sessionPromptVagueScores.push(vagueScore(text)); // vagueScore is already in scope
```

After the `sorted` loop closes, before `sessions.set(sessionId, sessionStat)`:

```typescript
sessionStat.effectivenessScore =
  totalSessionToolCalls >= MIN_TOOL_CALLS
    ? productiveToolCalls / totalSessionToolCalls
    : null;

// Lower-median for even N is intentional (consistent with existing avgPromptWords)
const sortedVague = [...sessionPromptVagueScores].sort((a, b) => a - b);
sessionStat.medianVagueScore =
  sortedVague.length > 0
    ? sortedVague[Math.floor(sortedVague.length / 2)]
    : null; // null = no user prompts in session; excluded from bucket aggregation
```

**Step 4: Aggregate effectivenessByBucket after the session loop**

Define `median()` as a module-level helper alongside `computeCost`:

```typescript
function median(arr: number[]): number | null {
  if (arr.length < 2) return null;
  const s = [...arr].sort((a, b) => a - b);
  return s[Math.floor(s.length / 2)]; // lower-median; intentional
}
```

After `for (const [, sess] of sessions)` totals are computed, add:

```typescript
const scoredSessions = Array.from(sessions.values())
  .filter(s => s.effectivenessScore !== null && s.medianVagueScore !== null);

const specificScores = scoredSessions
  .filter(s => s.medianVagueScore! < 3)
  .map(s => s.effectivenessScore!);
const vagueScores = scoredSessions
  .filter(s => s.medianVagueScore! >= 3)
  .map(s => s.effectivenessScore!);

const effectivenessByBucket = {
  specific: median(specificScores),
  vague: median(vagueScores),
};
const medianEffectivenessScore = median(scoredSessions.map(s => s.effectivenessScore!));
```

Add both to the `return { ... }` statement at the end of `analyze()`.

The diff value (`+0.29`) is `effectivenessByBucket.specific - effectivenessByBucket.vague`,
computed as a local variable in `render()` — not a field on `AnalysisResult`. It
is not exported; it exists only for display. `effectivenessByBucket` on
`AnalysisResult` holds the two medians; the diff is derived at render time.

Null handling: a bucket is null when N < 2 for that group. If either bucket is
null, show `—` for that row and omit the diff line. If `medianEffectivenessScore`
is null (no sessions reached MIN_TOOL_CALLS threshold), hide the panel entirely.

Null handling: if either bucket has N < 2, show "—" for that row and omit the
diff line. If no sessions scored (all < MIN_TOOL_CALLS), hide the panel entirely.

## Resolved Decisions

- **Per-session, not per-prompt.** `effectivenessScore` lives on `SessionStats`.
  A session's specificity bucket is determined by its median prompt vagueScore.
- **MIN_TOOL_CALLS = 5.** Sessions with fewer tool calls are excluded from scoring
  (exploratory/short sessions penalized unfairly by the ratio).
- **"Median diff," not "correlation signal."** The number displayed is
  `specific_median − vague_median`. Directional, honest, requires no statistical
  prerequisites from the reader.
- **Two buckets, not seven categories.** `effectivenessByBucket: { specific, vague }`.
  The PromptCategory breakdown is deferred to Approach B where session-level
  ground truth makes it more meaningful.

## Success Criteria

- `npm test` passes with new tests covering:
  - `effectivenessScore` calculation (null when < 5 tool calls, correct ratio otherwise)
  - `medianVagueScore` per-session computation
  - `effectivenessByBucket` aggregation (null when N < 2 per bucket)
  - Dashboard panel renders correctly when both buckets are null
- Dashboard shows the new panel on `npx cortext` with no new flags required
- In your own 30-day data: median diff between buckets is > 0.10 with N ≥ 5
  sessions per bucket (either direction validates the hypothesis)
