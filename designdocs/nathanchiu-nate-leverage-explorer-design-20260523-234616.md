## Problem Statement

cortext tracks token cost and behavioral patterns per session, but has no signal for
*which sessions actually mattered*. A $4 session that produced a merged PR is more
valuable than a $0.80 session that went in circles. Without shipping signal, cortext
can tell you what you spent but not whether it was worth it.

The goal: detect leverage in your CC conversation history — specifically, which prompt
behaviors correlate with sessions that led to commits that became merged PRs.

## What Makes This Cool

The chain: **CC session → git commit → GitHub PR → merge**.

No one has mapped this before. cortext already has the session data. `gh` has the PR
data. The gap between them is a 30-minute attribution window and a `git log` call.
The result: your personal "I prompt this way when I ship" pattern — discovered from
your own history, not from a benchmark.

## Constraints

- `gh` CLI must be installed and authenticated (graceful fallback to "n/a" if not)
- No GitHub API calls from cortext directly — `gh` is the bridge
- Attribution window heuristic (~30 min) needs to be tunable; initial value is a guess
- Content-level prompt parsing (Phase 2) deferred — v1 uses existing signals only:
  vagueScore, subagent invocations, /clear cadence, Write/Edit ratio
- Correlation stats (Phase B) require N ≥ 20 high-leverage sessions to be meaningful;
  cold-start problem acknowledged
- Must not break existing TUI dashboard — leverage is additive, not a replacement

## Premises

1. `cortext sync` can reliably walk: session cwd → `git remote get-url origin` →
   GitHub owner/repo → `gh pr list`. Derive cwd from entries[].cwd (not process.cwd()).

2. Session → commit attribution: sessions whose `endTime` falls within `windowMs`
   *before* a git commit timestamp are tagged as precursors — commits that land in
   the N minutes **following** session end. N-to-N mapping (multiple sessions can
   attribute to one commit; one session can precede multiple commits). Default window:
   30 min (tunable via `--window` on `cortext sync`).

3. Leverage quality hierarchy: merged_pr > open_pr > commit_only > no_commit.
   This 4-tier ranking is the ground truth the system optimizes against.

4. Prompt pattern features stay at tool-call + existing signal level for v1:
   vagueScore, subagent invocations, /clear count, Write/Edit ratio.
   Content parsing of prompt text is deferred to v2.

5. Output surface is a new "Leverage" view in the TUI alongside cost, behavioral
   health, and persona alignment.

## Approaches Considered

### Approach C: Retrospective Trace View (chosen first)
Show the chain rather than compute statistics. `cortext trace` renders a timeline:
each session linked to its downstream commit and PR.
"May 20 ($2.30, 47 min) → commit abc123 → PR #47 (merged May 22)"
- Effort: S (3-4 days: sync + attribution only, no correlation math)
- Risk: Low — attribution errors are visible and correctable
- Validation: you see whether the 30-min window is right before trusting it for stats

### Approach A: Session Leverage Tagger (second)
Add `leverageTier` to SessionStats. Four tiers: merged_pr / open_pr / commit_only /
no_commit. Show tier + cost in TUI session list. No correlation math yet.
- Effort: M (1 week after Approach C validates attribution)
- Risk: Low — gh fallback, no new types beyond SessionStats.leverageTier

### Approach B: Pattern Correlation Engine (third)
Full pipeline: sync → attribute → correlate → surface. For each behavioral feature,
compute rank correlation against leverage tier. Surface top 3 predictive features.
- Effort: L (2-3 weeks after Approach A ships)
- Risk: Med — meaningful only with N ≥ 20 high-leverage sessions

## Recommended Approach

**C → A → B, in sequence.** Validate the attribution model with your own eyes (C)
before trusting it enough to label sessions (A), before running correlation on it (B).

### New command: `cortext sync`

```typescript
// src/sync.ts
export async function syncGitHub(options: { windowMs: number }): Promise<void> {
  // 1. Collect unique cwds from session JSONL entries (last 30 days)
  //    e.g. new Set(readProjects(30).flatMap(p => p.entries.map(e => e.cwd).filter(Boolean)))
  const cwds = collectSessionCwds();

  // 2. Resolve cwds → unique "{owner}/{repo}" keys (deduplicate by remote, not by cwd)
  const repoKeys = new Set<string>();
  for (const cwd of cwds) {
    try {
      const remote = await run(`git -C ${cwd} remote get-url origin`);
      const key = parseGitHubRemote(remote); // returns "owner/repo" or throws
      repoKeys.add(key);
    } catch {
      // cwd no longer exists or is not a git repo — log warning, skip
      console.warn(`[cortext sync] skipping stale cwd: ${cwd}`);
    }
  }

  // 3. For each unique repo, skip if cache is < 1 hour old
  const cache = loadPrCache(); // reads ~/.cortext/pr-cache.json or returns empty
  for (const key of repoKeys) {
    const cached = cache.repos[key];
    if (cached && Date.now() - cached.syncedAt < 60 * 60 * 1000) continue; // cache hit

    // 4. Fetch PRs via gh (MERGED + OPEN), build prsByCommit index
    const [owner, repo] = key.split('/');
    const rawPrs: PrEntry[] = JSON.parse(
      await run(`gh pr list -R ${key} --state all --json number,title,state,mergedAt,commits --limit 100`)
    );
    // Note: gh pr list may truncate commits for old/large PRs. If a commit SHA is
    // missing from the index, fall back to gh pr view <number> --json commits for
    // individual PRs before reporting "commit_only."

    const prsByCommit: Record<string, PrEntry[]> = {};
    for (const pr of rawPrs) {
      for (const commit of (pr as any).commits ?? []) {
        const sha: string = commit.oid ?? commit.sha;
        (prsByCommit[sha] ??= []).push(pr);
      }
    }

    cache.repos[key] = { syncedAt: Date.now(), prsByCommit };
  }

  savePrCache(cache); // writes ~/.cortext/pr-cache.json
}
```

### Attribution logic

```typescript
// src/leverage.ts
export function fetchRecentCommits(cwd: string, sinceMs: number): GitCommit[] {
  // git log for commits after (sinceMs - 2h buffer) so the window can reach back
  const since = new Date(sinceMs - 2 * 60 * 60 * 1000).toISOString();
  const raw = runSync(`git -C ${cwd} log --after="${since}" --format="%H %at %s"`);
  return raw.trim().split('\n').filter(Boolean).map(line => {
    const [sha, ts, ...msg] = line.split(' ');
    return { sha, timestamp: Number(ts) * 1000, message: msg.join(' '), repoKey: resolveRepoKey(cwd) };
  });
}

export function attributeSessionToCommits(
  session: SessionStats,    // session.endTime: number (Unix ms)
  commits: GitCommit[],
  windowMs: number = 30 * 60 * 1000
): GitCommit[] {
  // Commits whose timestamp falls in (session.endTime, session.endTime + windowMs]
  return commits.filter(c =>
    c.timestamp > session.endTime &&
    c.timestamp <= session.endTime + windowMs
  );
}

export function resolveLeverageTier(
  commits: GitCommit[],
  cache: PrCache
): LeverageTier {
  if (commits.length === 0) return 'no_commit';
  const repoKey = commits[0].repoKey;
  const prsByCommit = cache.repos[repoKey]?.prsByCommit ?? {};
  const prs = commits.flatMap(c => prsByCommit[c.sha] ?? []);
  if (prs.some(pr => pr.state === 'MERGED')) return 'merged_pr';
  if (prs.length > 0) return 'open_pr';
  return 'commit_only';
}
```

### New command: `cortext trace`

Respects the global `--days` flag (defaults to 30). Optional `--verbose` adds the
session JSONL path for debugging attribution errors.

Output format:
```
Project            Session               Cost    Duration  Chain
───────────────────────────────────────────────────────────────────────────
cortext            May 20 14:32          $2.30   47 min    → commit abc1234 → PR #47 ✓ merged May 22
cortext            May 19 09:15          $4.10   2h 3min   → no commit
cortext            May 18 16:44          $1.20   28 min    → commit def5678 → PR #45 (open)
cortext            May 18 11:02          $0.80   15 min    → commit ghi9012 (no PR)
```

Note: "no commit" is a factual label. Whether that session was useful is for you to
judge — exploration, research, and failed experiments all produce no commit.

### Open Questions

1. **Attribution window**: 30 min is a guess. `cortext sync --window 60` should be
   supported. After Approach C ships, validate against your own history and adjust.

2. **Multi-repo sessions**: A session where you switch between repos (different cwds)
   — which repo do you attribute commits to? Current plan: tally tool calls per cwd,
   pick the mode cwd, resolve its repoKey. Sketch:
   `const modeCwd = maxBy(Object.entries(toolCallsByCwd), ([, n]) => n)?.[0]`
   then `fetchRecentCommits(modeCwd, windowMs)` for attribution.

3. **Subagent sessions**: Subagent JSONL files live in
   `~/.claude/projects/{project}/{sessionId}/subagents/`. The learning from your
   codebase says detection requires checking for a subagents/ subdir. Should subagent
   sessions be attributed separately or rolled into the parent session?

4. **gh not installed**: `cortext sync` should fail gracefully with a helpful error
   ("Install gh and run `gh auth login` to enable leverage tracking") not a stack trace.

5. **PR lag**: A session on May 20 might lead to a PR that gets merged on June 3.
   The `cortext trace` output should show "pending" for open PRs and update on each
   `cortext sync` run.

## Success Criteria

- `cortext trace` renders the session → commit → PR chain for the last 30 days
- Attribution window is tunable via `--window N` flag (on `cortext sync`)
- Attribution accuracy is visually verifiable — Project + Session columns make
  it obvious when a session is wrongly attributed; `--verbose` adds the JSONL path
- `cortext sync`: first sync < 10 seconds per repo for 100 PRs; subsequent syncs
  within 1 hour are instant (cache hit — repo is skipped entirely)
- `gh` absence or stale cwd produces a clear warning per-repo, not a silent failure
  or a crash

## The Assignment

> **Before writing a line of code:** run `git log --oneline --after="1 month ago"`
> in your main repo and count your commits from the last 30 days. Then open cortext
> and look at your session list for the same period. Try to match at least 5 commits
> to sessions by hand — just looking at timestamps. If you can match more than half
> of them this way, the 30-min attribution window is plausible and the model is worth
> building. If you can't match them even manually, the window assumption is wrong and
> needs rethinking before a line of sync code is written.
