## Problem Statement

cortext measures how you prompt: vagueness, correction rate, session effectiveness via
tool call ratio. That's the human input layer. What it doesn't measure yet is the
environment layer — whether the harness was configured to let you do your best work.
CLAUDE.md structure, hooks, subagent patterns, permission modes: these shape what Claude
can do before a single prompt fires. Nobody is measuring them alongside prompt quality.

The two layers belong together. A high vagueness score looks different if your CLAUDE.md
is 2000 words of noise — maybe the prompts were vague because Claude had bad context to
work from. cortext adds a second analytics layer, not a replacement for the first.

The insight from the Anthropic engineering blogs: the 20x quality gap in their DAW example
came from architecture (generator-evaluator), not better prompting. Config is the cause;
session behavior is the symptom. cortext currently measures the symptom. This design moves
it to the cause.

## What Makes This Cool

A developer runs `npx cortext` and sees two things they've never seen before:

1. **Config audit**: "You have no hooks configured. Your CLAUDE.md is 847 words with no
   subdirectory files. LSP integration: not detected."

2. **Behavioral patterns**: "Sessions with subagent usage (12 of your last 30) had 2.3x
   higher write/edit tool ratio than single-agent sessions. Your compaction events cluster
   on Tuesdays — you're hitting context limits on long sessions."

Nobody in the developer analytics space has this. Every other tool measures AI output quality.
cortext already measures human input quality (how you prompt). Now it also measures the
environment quality (how your setup shapes what's possible). Both layers in one tool.

The "aha" moment: **the gap between your harness and the Anthropic best-practice baseline
is now a number.** Not just qualitative advice — a score tied to documented recommendations.

## Constraints

- Works entirely from existing data: `~/.claude/projects/` JSONL + `~/.claude/` config files
- Zero onboarding friction — `npx cortext` gets the new panels on next run
- No backend, no accounts, no telemetry
- Weekend-scale build (M effort: 1-2 weekends)
- Anthropic's published best practices (harness design blog + large codebase blog) are the
  scoring source of truth — not opinion-based heuristics

## Premises

1. The behavioral harness signals detectable in JSONL are: subagent usage (parent/child
   session relationships), compaction events (summary entries), session resets, and tool
   call diversity (unique tool namespaces used per session). Hooks running and CLAUDE.md
   loading are NOT directly visible in JSONL — those come from config analysis.

2. Static config analysis (reading CLAUDE.md, .claude/settings.json, .claudeignore) is
   the higher-value signal. It shows setup intent; JSONL shows outcome. Both are needed.

3. The scoring rubric should track Anthropic's published docs, not internal opinion. This
   makes it credible and means it improves as Anthropic publishes more.

4. M effort — the config-reading surface area is new for cortext. Plan for 1-2 weekends.

5. You are user #1. Run this on cortext's own harness before any claims about usefulness.

## Landscape Context

Two Anthropic reference posts define the harness engineering space:

**"Harness Design for Long-Running Apps"** (Anthropic Engineering Blog)
- Generator-evaluator architecture outperforms single-agent by eliminating self-praise bias
- Context anxiety (premature session wrap-up) is a real, detectable failure mode
- Harness is perishable: must be revisited with each model release
- Key detectable signals: multi-agent sessions, compaction events, cost-per-session patterns

**"How Claude Code Works in Large Codebases"** (Claude Blog)
- Seven-component harness: CLAUDE.md, hooks, skills, plugins, LSP, MCP, subagents
- Stop hooks are explicitly the right place for post-session reflection
- CLAUDE.md root file: "pointers and critical gotchas only" — length is a proxy for health
- Biggest anti-pattern: using prompts for things that should run automatically (hooks)

**EUREKA**: Most tools assume you need behavior data to understand quality. But the config
files are the actual diagnosis — they exist before any session fires. Harness health is
primarily a setup question, secondarily a behavioral one. cortext currently measures
behavioral symptoms; this design adds the causal layer.

**Second EUREKA**: Harness scoring is a moving target. Blog 1 explicitly states: "scaffolding
built for old model limitations becomes overhead or actively harmful with new models." A
harness score that was green for Sonnet 4.5 may be yellow for Opus 4.6. cortext's CLAUDE.md
already designates the best practices docs as the source of truth — the scoring system should
track the same docs and update when they do.

## Approaches Considered

### Approach A: Behavioral Fingerprint Only (rejected)
Parse JSONL only. Add: subagent session detection, compaction event count, tool namespace
diversity, session reset frequency. New TUI panel.
- Effort: S (2-3 days)
- Risk: Low — pure extension of existing patterns
- Rejected: misses the higher-value config signals; power users immediately ask "why doesn't
  this read my CLAUDE.md?"

### Approach B: Full Harness Health — Config + Behavioral (chosen)
Config audit module reads `~/.claude/settings.json`, root `CLAUDE.md`, `.claudeignore`,
and checks for hooks, MCP servers, skills. JSONL behavioral analysis adds subagent patterns,
compaction events, context anxiety signals. Combined TUI panel with per-component scores.
- Effort: M (1-2 weekends)
- Risk: Medium — new config-reading surface area; scoring criteria need maintenance as docs update

### Approach C: Stop Hook Advisor
cortext ships a pre-built stop hook. After every CC session, fires automatically and outputs
a harness health note. Ambient rather than on-demand.
- Effort: M — but architecturally different; no TUI dashboard
- Deferred: distribution friction (requires users to modify settings.json); harder to dogfood
  before publishing. Natural evolution of Approach B after v1 proves useful.

## Recommended Approach

**Approach B: Full Harness Health.**

Combined config + behavioral view because: (1) the EUREKA established config as the causal
layer — measuring only symptoms undershoots the insight; (2) the user already committed to
the combined view; (3) cortext's existing SOT declaration in CLAUDE.md makes the scoring
approach credible without being opinionated.

**Reading config files:**

```typescript
// src/harness.ts — auditConfig()
import { readFileSync, existsSync } from 'fs';
import { homedir } from 'os';
import path from 'path';

const CLAUDE_DIR = path.join(homedir(), '.claude');

function auditConfig(cwd: string): ConfigAudit {
  // Global settings: ~/.claude/settings.json
  // Project settings: {cwd}/.claude/settings.json — check both, merge
  function loadSettings(p: string): Record<string, unknown> {
    if (!existsSync(p)) return {};
    try { return JSON.parse(readFileSync(p, 'utf8')); }
    catch { return {}; }  // corrupted settings.json should not crash npx cortext
  }

  const globalSettings = loadSettings(path.join(CLAUDE_DIR, 'settings.json'));
  const projectSettings = loadSettings(path.join(cwd, '.claude', 'settings.json'));
  // Project settings take precedence; merge for presence checks
  const merged = { ...globalSettings, ...projectSettings };

  const rootMdPath = path.join(cwd, 'CLAUDE.md');
  const globalMdPath = path.join(CLAUDE_DIR, 'CLAUDE.md');
  const mdPath = existsSync(rootMdPath) ? rootMdPath
               : existsSync(globalMdPath) ? globalMdPath
               : null;

  return {
    hasRootClaudeMd: mdPath !== null,
    claudeMdWordCount: mdPath
      ? readFileSync(mdPath, 'utf8').split(/\s+/).filter(Boolean).length
      : null,
    hasSubdirectoryClaudeMds: false, // TODO v2: traverse subdirs
    hasHooks: (() => {
      // CC hook schema: settings.json { "hooks": { "PreToolUse": [...], "PostToolUse": [...], "Stop": [...] } }
      // Key casing is unverified on this machine — no hooks are configured in ~/.claude/settings.json.
      // Detection uses case-insensitive key search to avoid silent wrong scores.
      const hooks = (merged as any)?.hooks ?? {};
      const find = (key: string) => {
        const lk = key.toLowerCase();
        const match = Object.keys(hooks).find(k => k.toLowerCase() === lk);
        return match ? Array.isArray(hooks[match]) && hooks[match].length > 0 : false;
      };
      return {
        preToolUse: find('pretooluse'),
        postToolUse: find('posttooluse'),
        stop: find('stop'),
      };
    })(),
    hasDenyPermissions: Array.isArray((merged as any)?.permissions?.deny)
      && (merged as any).permissions.deny.length > 0,
    hasClaudeIgnore: existsSync(path.join(cwd, '.claudeignore')),
    mcpServerCount: Object.keys((merged as any)?.mcpServers ?? {}).length,
  };
}
```

**Detecting subagents in JSONL (verified field names):**

Subagent JSONL files live in subdirectories: `~/.claude/projects/{project}/{sessionId}/subagents/agent-{agentId}.jsonl`. Their entries have `isSidechain: true`. A session spawned subagents if its session ID directory contains a `subagents/` folder with at least one file.

```typescript
// In src/reader.ts (or new harness reader) — detect subagent sessions
import { readdirSync, statSync } from 'fs';

function hasSubagents(projectDir: string, sessionId: string): boolean {
  const subagentDir = path.join(projectDir, sessionId, 'subagents');
  try {
    return statSync(subagentDir).isDirectory()
      && readdirSync(subagentDir).length > 0;
  } catch {
    return false;
  }
}
```

**Scoring `computeHarnessScore()` body sketch:**

```typescript
function computeHarnessScore(config: ConfigAudit, behavioral: BehavioralProfile): HarnessScore {
  // Config score: points out of 100
  let configScore = 0;
  if (config.hasRootClaudeMd) configScore += 25;
  if (config.claudeMdWordCount !== null) {
    if (config.claudeMdWordCount < 500) configScore += 15;
    else if (config.claudeMdWordCount <= 1500) configScore += 8; // yellow partial
    // > 1500: 0 pts (bloat)
  }
  // When claudeMdWordCount is null (no CLAUDE.md), the 15 pts are simply not awarded —
  // the denominator stays 100 so the penalty is captured in the hasRootClaudeMd row already.
  if (config.hasHooks.stop) configScore += 20;
  if (config.hasHooks.preToolUse || config.hasHooks.postToolUse) configScore += 10;
  if (config.hasClaudeIgnore) configScore += 10;
  if (config.hasDenyPermissions) configScore += 10;
  if (config.mcpServerCount > 0) configScore += 10;

  // Behavioral score: points out of 100
  const totalSessions = /* passed in from analyzer */ 0; // replace with real count
  let behavioralScore = 0;
  if (totalSessions > 0) {
    const subagentRate = behavioral.subagentSessionCount / totalSessions;
    if (subagentRate > 0.20) behavioralScore += 50;
    else if (subagentRate >= 0.05) behavioralScore += 25; // yellow partial
  }
  // Compaction: 0 = informational (not penalized for short projects), not red
  if (behavioral.compactionEventCount > 0) behavioralScore += 30;
  // else: 0 pts, no penalty marker — display "(0 compaction = normal for short projects)"
  if (behavioral.toolNamespaceCount > 3) behavioralScore += 20;
  else if (behavioral.toolNamespaceCount >= 2) behavioralScore += 10; // yellow partial

  const overall = Math.round(0.6 * configScore + 0.4 * behavioralScore);

  return {
    config,
    behavioral,
    configScore,
    behavioralScore,
    overall,
    missingComponents: [
      !config.hasHooks.stop && 'stop hook',
      !config.hasRootClaudeMd && 'CLAUDE.md',
      !config.hasClaudeIgnore && '.claudeignore',
    ].filter(Boolean) as string[],
    strengths: [
      behavioral.subagentSessionCount > 0 && 'subagent usage',
      behavioral.compactionEventCount > 0 && 'context compaction',
      config.mcpServerCount > 0 && 'MCP servers configured',
    ].filter(Boolean) as string[],
  };
}
```

## Open Questions

1. **Settings.json hook key casing**: The global `~/.claude/settings.json` on this machine
   has no `hooks` key — it only has `enabledPlugins` and `extraKnownMarketplaces`. Hook
   configuration may live in project-level `.claude/settings.json` only, or may use different
   key casing than assumed (`PreToolUse` vs `preToolUse`). Verify by running
   `cat ~/.claude/settings.json | python3 -m json.tool` before assuming the schema.

2. **Context anxiety signal (deferred to v2)**: The proxy would be "sessions with total
   tokens > 100k AND short duration." This requires correlating `system/turn_duration`
   entries (which contain `durationMs`) with per-session token totals. Deferred — do not
   include `contextAnxietySignals` in v1 types.

3. **Scoring thresholds are v1 heuristics**: The point values and green/yellow/red
   thresholds are derived from the two blog posts and will need calibration after running
   on real data. Treat them as versioned defaults, not truth. Plan for a config override
   mechanism in v2.

4. **Subdirectory CLAUDE.mds (deferred to v2)**: Detection requires traversing the project
   directory tree. The `hasSubdirectoryClaudeMds` field should be hardcoded `false` in v1
   with a `// TODO v2` comment.
